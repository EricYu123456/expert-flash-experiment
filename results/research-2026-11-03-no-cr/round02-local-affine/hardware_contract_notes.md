# Hardware assumptions for a later positive expansion

This is symbolic design review after the thinking gate, not a model probe or a change to the frozen Stage0 algorithm. The operator pilot cannot establish physical AiF latency.

The source paper exposes a chip GEMV dimension, block ID, offset and sequential page count. It does not expose the short-input wire ABI, minimum width, PE lanes, arithmetic scaling, FIFO drain, multi-plane address restrictions or launch timing. Typical8–32KiB inputs are not a documented minimum. Support for r64/r128 must be an explicit implementation contract, possibly a controller/firmware change, rather than assumed free or declared to require new silicon without evidence.

An implementation of the numerical contract needs signed-I8 products with sufficient exact accumulation (I32 is sufficient for the tested dimensions), followed by the declared host F32 scale and bias operations. Original publication arithmetic widths and scale representation remain unverified. One shared centered input context per participating plane is sufficient for the primary map epoch; K unrelated retained inputs are not assumed. A mixed original/map layer may need a new input epoch and input reloads.

At H2048/r128, complete rows give128 rows per16KiB page,16 pages per map, and a g4 layout with4 pages per participating chip. With g2/r64 the corresponding values are256 rows/page,8 pages/map and4 pages/chip. These are constructions in an explicit row/I8/page model, not measured four-plane timing. Same-page/block multi-plane restrictions must be satisfied by physical allocation, or the plan pays extra waves. All controls receive the same legal allocation and replication ability.

For illustration only, four complete g4 replicas of every Deep r128/C32 map cost about55.8decimalGB of raw coefficients before originals, scales, biases, ECC/spare and metadata. Four disjoint groups can serve at most four distinct maps per ideal wave; K6/K8 therefore need at least two such waves, plus real commands, input and output traffic. The native baseline gets the same capacity budget. No prior placement solver is a contribution of this candidate.

The paper stores generated results in an output FIFO, with SREG tracking status; it does not require an entire result vector to fit in SREG. Thus the greater number of rows per short-input page does not itself invalidate a map. It can increase drain/backpressure frequency and must be costed. Assuming4-byte results, each map emits8192bytes, with2048bytes/chip in g4 or4096bytes/chip in g2. This is an explicit payload assumption, not the publication's verified output dtype or FIFO throughput. The2GB/s/channel figure is a transfer limit, not total launch/drain latency.

ECCLITE6.4GB/s and the effective CR-plus-be-enc bandwidth do not establish PE throughput or ordinary-read bandwidth. A latency evaluation must expose/sweep unresolved compute, command, drain and posting parameters, and include a conservative supported-ABI scenario. It must not silently substitute the ECC rate for any of them.

Deep's unchanged shared2816 branch retains its own GU-to-Down dependency. The pilot only removes the dependency of each replaced routed expert. OLM without shared experts can remove the whole routed-FFN barrier only when all selected experts use maps. A layer-synchronous guard can synchronize eligibility, but eight pilot operators do not establish whole-layer map quality or availability for64 experts.

W4 is a necessary quality/control question, not automatic native AiF throughput. INT8 PEs do not establish packed-nibble execution for free. A row-scaled packed-W4 path needs a specified unpack/sign-extension contract and its throughput/area. A stronger group-scaled quantizer may also need group partial sums, scale handling or host reduction, which changes output traffic and arithmetic. Candidate W4 maps receive the same capability. Do not assign half the pages to an unimplemented W4 numerical format and call the result an actual native control. Conversely, do not dismiss a feasible small unpack/scale extension when the user explicitly permits small hardware changes.

Measured CPU numerical execution, modelled flash service/DAG time, actual NVMe queue/emulator overhead and real AiF-chip measurements are separate evidence. Existing project NVMeVirt records validate metadata commands and counters; they do not supply a real numeric AiF implementation. In particular, dummy outputs cannot supply correct future dynamic MoE routes or candidate free-running quality. Use actual numeric trajectories and explicit timing integration for any later system claim.
