# Source-native Q4_K/Q6_K on ordinary NAND: focused prior and feasibility screen

Source-only screen, recorded 2026-11-03 UTC. No model, weight, activation, candidate execution or quality data was inspected. This is **not** a candidate adoption or an experiment.

## Verdict

**Merely porting an activation LUT to the die is a weak research claim.** Close primary precedents already build activation-dependent lookup tables near memory, account for lookup generation, reuse inputs, or fuse/stream FFN work. The strongest potentially testable remaining question is narrower: can an explicitly costed, ordinary-read NAND implementation serve *the original block-quantized arithmetic* while overlapping a 256-neuron GU-to-Down frontier, beating both (i) an equal-area compressed-code expander plus direct MAC with the **same frontier and layout**, and (ii) a strong same-format ordinary loader and host execution? It must account for table posting or local generation, SRAM/read ports, metadata, ECC, correct partial sums and traffic. Shared LUT generation across expert-private weights alone is not an adequate novelty claim. The search below does not establish global novelty or absence of an artifact.

This comparison might show little benefit: both die approaches sense the **same compressed source bytes**; a LUT does not automatically save a NAND read. If ordinary sensing dominates and MAC work can be hidden, LUT acceleration may not improve latency; if PE service is exposed, direct low-bit expansion plus extra MACs may win instead. Neither overlap nor a particular AiF PE rate has been established. Stage timing needs a supported resource/dependency schedule, not an assumed `max(tR, compute)`.

## The source format is more than packing four-bit values

`QK_K=256`. Q4_K stores 256 weights in 144 bytes: 128 bytes of nibbles, 12 bytes packed group scales/minima, and two FP16 superblock values. Eight 32-weight groups are affine: `w = d * scale * q - dmin * min`. Accordingly, the dot includes the input-sum correction, as the generic CPU dot function shows. Q6_K stores 256 weights in 210 bytes: 128 low-code bytes, 64 high-code bytes, 16 signed group scales, and one FP16 superblock value. Extracting `((low4 | high2<<4) - 32)` and respecting 16-weight group scales is required. The layouts and [dequantization](https://github.com/ggml-org/ggml/blob/facdc44a67da17df4433adcc468b424f48e9ded2/src/ggml-quants.c#L1940) are explicit.

The public reference Q8_K quantizer chooses its scale using the maximum absolute activation **per 256-value block**, with its own signed-max, rounding and zero-block rules, and records group-of-16 sums. Thus in this particular contract a downstream block can become numerically ready when its own 256 original-order activation values are ready: an all-neuron amax barrier is not logically required. This is conditional on the real executor actually selecting that quantizer and accepting blockwise output/partial sums; it is not proof of an AiF command ABI. Moving neurons across Q8_K blocks changes their activation grouping/scales. Reordering complete blocks while preserving their internal order avoids that issue, but changing floating-point accumulation order/FMA can still change outputs. Integer identity is not a floating-point bit-exact guarantee; need an explicit reference, overflow widths, reduction order and IEEE/nonfinite behavior.

For H=2048, a Q4_K row has eight blocks = 1152 bytes. A 16 KiB page holding whole rows holds 14 such rows with 256 bytes unused; other packing could use cross-page continuation. For a Q6_K Down matrix with 1024 input columns, an output row has four 210-byte blocks; serving a single 256-column frontier across many outputs requires an actual block-major physical mapping or gathering, and physical block order must retain all per-block metadata. Whole-block reordering is storage-representation preserving, but its page padding, striping, FTL/ECC, row IDs, command and continuation overhead must be paid by **both** in-flash and ordinary-loader baselines. These byte examples do not prove a physical wave count or a numerical speedup.

## Concrete LUT accounting, not an asserted architecture

One exact integer construction uses four Q8 activation codes `a0..a3` and `L(mask)=sum_j a_j*bit(mask,j)` for all 16 masks. Every table entry lies within [-512, 508], so a signed 16-bit entry is safe. For unsigned Q4 code bit planes `mask_b`, `sum_j a_j*q_j = sum_(b=0..3) 2^b L(mask_b)`; Q6's six unsigned bit planes additionally need its `-32*sum_j a_j` term before the signed group scale. This identity preserves the integer dot; it does **not** by itself prove identical floating outputs.

At H=2048, `2048/4 * 16 * 2 = 16 KiB` of tables per logical activation vector, plus activation block scales, sums, staging and control. A single 256-element tile needs 2 KiB of LUT entries, but tiling changes the schedule and may force extra input/table posting or rereading. Q4 needs four table reads per four weight codes and Q6 six; mask extraction and reduction/shift remain. Simultaneous throughput depends on LUT bank conflicts, port count, broadcast, and multi-lane access. A NAND page-buffer latch is not automatically a random-access, multiported 16 KiB SRAM. If a table is generated in each die, provide generator/area/energy and build latency; if built by host, charge the transfer and duplication across dies/channels. Both alternatives must pay ECC and metadata consumption with explicit buffer lifetimes. No AiF source inspected establishes these new ports, capacities or overlap.

All routed GU projections that consume an identical input can mathematically share that vector's LUT, including an applicable shared expert; a precondition is that layout, input quantizer and schedule allow it. Each expert's Down input follows its own gate/up/SiLU and requires a different LUT; building and posting per expert and per 256-value frontier is not free. The table and an input page/cache/weight buffer/output accumulator can compete for the same storage/ports; explicitly distinguish new RF/SRAM from existing latches and charge ECC before code consumption unless a correct late-patch design is separately established.

## Controls and falsification

* **Same die area and schedule:** compressed-source ordinary-sense pagebuffer, Q4/Q6 decoder, group scale/min logic and sufficient direct integer MAC lanes, with identical ECC, page mapping, frontier, latches, accumulator and numeric contract. The LUT candidate pays full generator, table storage, ports, mask shuffling, scales/min corrections, control and output bandwidth. Avoid comparing a fully provisioned LUT against a deliberately serial expander.
* **Same-format ordinary host:** compressed Q4_K/Q6_K files, optimized block dot and host input reuse, real page/PCIe/CPU/cache accounting. Compare against known CPU LUT as well as optimized SIMD dot where format-compatible. **All-host OLM** must include fixed/shared operators and complete end-to-end I/O, not just selected expert GEMVs.
* **Same nonlinear graph:** both variants get 256-neuron GU frontier, Q8_K quantization, Down partial sums, scheduling freedom and matching GGUF reordering. If the chosen backend instead uses full-expert dynamic A8, use that actual barrier for both. Account for extra partial output storage/traffic and required support for block continuation. Verify mathematically and against the specified backend before claiming exactness.
* **Veto criterion:** if table posting/generation plus multiport RF exceeds direct-MAC time/area benefit or neither design improves exposed end-to-end latency over the ordinary host at equal resources, do not promote the LUT port as the method. If a synthesis/functional prototype is ever authorized, it needs measured table port conflicts, PE rate, ECC/service schedule and full FFN timeline; no such measurement is made here.
