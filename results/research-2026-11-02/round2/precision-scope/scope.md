The present results compare physical placements under an explicit INT8 architectural timing model, driven by real routes from fixed llama.cpp checkpoints. They do not demonstrate native AiF inference of those same numerical checkpoints. The existing README already separates routing precision and modeled weight precision; this audit makes the resulting limitation explicit.

All six local GGUF headers were read independently and matched against the existing metadata: every tensor name, shape, type, payload byte count and absolute offset agreed. This read 17,817,351 bytes of headers twice, with no tensor payload reads. Full-file SHA values below are recorded download/conversion provenance, not newly recomputed hashes. This audit did not read route arrays, evaluate test prompts, change a frozen layout, or rerun timing results.

See the [official Qwen configuration](https://huggingface.co/Qwen/Qwen3-30B-A3B-Instruct-2507-FP8/blob/5a5a776300a41aaa681dd7ff0106608ef2bc90db/config.json).

Q8_0 is not a scale-free I8 matrix. Its block contains 32 signed quants plus one FP16 scale: 34 bytes for 32 logical weights, 6.25% more than the modeled raw I8 payload before page packing. A Q8_0 × Q8_0 CPU dot has the mathematical form

`y_i = sum_b dW[i,b] * dX[b] * sum_(k=0..31) qW[i,b,k] * qX[b,k]`.

The actual CPU implementation also determines floating-point reduction order. The modeled full I8 GEMV has one integer sum across columns and does not represent these per-block scales. A single host scale after that full sum cannot reproduce arbitrary per-block scaling. Existing dense GEMVs plus host-scaled partial sums are a possible software composition, but their input/output traffic, commands, scale handling and numerical order need separate accounting. This audit does not assert that such a composition requires a new PE operator.

For the three Q4_K_M routing checkpoints, packed expert projection bytes total 0.60546875 times the modeled I8 bytes; for the three Q8_0 checkpoints they total 1.0625 times the modeled bytes. These ratios describe different numerical representations. They are not correction factors that make the present timing model an execution model of the GGUF files. CPU dot traits use Q8_0 activation blocks for Q8_0 weights and Q8_K for Q4_K/Q6_K weights, rather than a recorded, fixed, scale-free AiF A8 activation stream. No independent native AiF W8A8 routing run or full-model matched numerical validation was found in the audited provenance. Sampled BF16/FP8-to-Q8_0 conversion checks validate the converter, not model quality or AiF execution.

The published AiF paper describes INT8 multipliers, an adder tree, GEMV addressing, sequential output FIFO and a host output-buffer address. It also discusses partitioning a projection between host and SSD and aggregating the results. It does not establish the accumulator width, output FIFO element dtype/width, overflow behavior, block-scale arithmetic, or rounding/requantization contract needed for a numerical equivalence proof. Its virtual evaluation explicitly generates dummy output vectors. See [AiF, ISCA 2025](https://doi.org/10.1145/3695053.3731073), Sections 4.2 and 5.2; the locally archived text is `paper/aif.txt`, lines 776–823 and 847–882. This is an evidence gap, not proof that the real PE cannot support a particular output format.

The local `kernel/aif.h` explicitly states “Metadata only: no weights or GEMV outputs.” Its v2/v3 `output_bytes` fields are counters; `kernel/aif.c` returns completion status and a target time. The modeled four bytes per output element in `joint_plane_search.py` therefore establishes neither FP32 nor raw I32 output. Metadata replay cannot validate either datatype. The local model also uses 6.4 GB/s as a service ceiling, rather than measuring PE throughput or a disclosed MAC-lane count.

Column splitting with dense GEMV plus host partial sums remains within the existing operator vocabulary. As one conditional exact case, a 512-wide signed-I8 dot has absolute value at most `512*128*128 = 2^23`. If the native interface returns that unscaled integer as exact I32 or FP32, host I64 accumulation and one specified final rounding can recover a full raw-I8 dot. If each tile result is scaled, rounded or requantized first, that proof does not apply. The human user did not prohibit host partial sums or floating-point reordering; prior bit-exact restrictions were a conservative research choice. Any tolerated numerical change must instead be defined and evaluated with model quality.

The smallest useful next routing experiment is available without designing new quantization: IBM's [official G4 GGUF repository](https://huggingface.co/ibm-granite/granite-4.0-h-tiny-GGUF/tree/08d5a8a9741dd5c1a95d2d39e25253226aa1464e) contains `granite-4.0-h-tiny-Q8_0.gguf`, 7,390,331,744 bytes, SHA-256 `6d89e0698c7e88ebe26efcf59aa22786bf36b729705edbd76c6b118c8df9b297`, at the same pinned revision as the current Q4_K_M. It also contains a 13,891,206,272-byte BF16 GGUF. The official source repository reports 6,939,037,248 BF16 parameters at revision `791e0d3d28c86e106c9b6e0b4cecdee0375b6124`. AllenAI likewise offers an [official OLMoE Q8_0 GGUF](https://huggingface.co/allenai/OLMoE-1B-7B-0924-GGUF/tree/70df85ed7132bf21b5acbcb33817f58e7d3cb949), 7,359,942,240 bytes. These availability statements were checked using official repository API metadata only; no weight download was performed.

For G4, freeze the existing methods first, then compare Q4_K_M and pinned Q8_0 on the same existing 32 training prompts × 64 steps and a prospectively selected disjoint public set. For example, 32 new public prompts would produce 4,096 traced decode steps across two precisions, plus the per-checkpoint untraced instrumentation controls. Freeze public IDs, tokenization, scoring and compute budget before opening outputs; the existing repeatedly inspected public set is not a fresh holdout. Independent greedy generation measures the actual execution route distribution; a common teacher-forced token sequence, if supported by the collector, separates route sensitivity from autoregressive token divergence. Record traced/untraced token equality within each checkpoint, top-k overlap, activation/routing precision settings, and modeled latency of every frozen placement without fitting to the public set. Q4 and Q8 generated tokens are not expected to match each other. A quality claim needs task scoring or a suitable likelihood/accuracy evaluation, not routing overlap alone.

That experiment would strengthen precision robustness of the placement observations. It would still not establish native W8A8 numerical matching. A same-compute-model claim additionally requires a documented native I/O/scale/accumulation contract and a reference implementation of that contract, operator numerical checks, and full-model quality validation. Until then the honest scope is a trace-driven INT8 architectural placement study. Full-row relocation preserves the abstract dot without introducing a new within-row reduction, while native execution of the scaled routing checkpoint remains unvalidated.
