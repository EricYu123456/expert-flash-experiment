# AiF short-vector hardware contract: source-only audit

2026-11-03 UTC. Scope: source/document review only; no model, PG-19 text, quality output, candidate experiment or simulator was run. This audit distinguishes the published AiF architecture, a later reproduction's software decisions, and proposed new contracts. Unsuccessful source searches are not proof that an artifact does not exist.

## Closest primary sources and what is actually established

1. [AiF paper, ISCA 2025 §§4.4–6.1](https://doi.org/10.1145/3695053.3731073); locally `paper/aif.txt`, lines 724–782 and 810–927. Each AiFChip receives a GEMV command specifying an input-vector dimension, block ID, block offset, and number of pages, then the controller loads an input vector into page-buffer latches; the paper calls vector size *typically* 8–32 KiB. Plane matrix segments are corrected by ECC, passed with the input to INT8 multiplier/adder-tree PEs; output elements enter a FIFO and the controller polls chips round-robin; SREG tracks FIFO **status**. Host-level `aif_post` carries matrix dimensions, matrix host address and sequential LBA range; `aif_gemv` carries input dimension, input host address, matrix LBA range and output host address. Nothing in the described protocol proves vector payload encoding, byte count, fixed alignment, minimum or maximum dimension, row reset boundary, multiple complete rows per data page, endianness, output type, scale metadata or accumulator width. In particular, “typically 8–32 KiB” is not a demonstrated minimum and is not evidence that 128-byte vectors are rejected. Likewise, the existence of an input dimension is not proof 128-byte packed A8 is accepted.

2. **Implementation versus simulation.** AiF reports 45 nm Verilog synthesis at 200 MHz, PE area 0.026 mm² and power 3.98 mW per AiFChip in Table 1; it does not state the number of INT8 multipliers/MAC lanes, number of per-plane concurrent lanes, pipeline latency, or their sustained throughput. ECCₗᵢₜₑ is BCH 10 bits/1 KiB at **6.4 GB/s decoder throughput**, not a measured PE MAC rate. AiF §6.1 reports an NVMeVirt timing emulator returning **dummy** output vectors, not functional in-flash GEMV or numerical validation. Its simulated end-to-end rates are not a source for r128 row timing or realistic runtime MoE routing from true GEMV values. 16 chips, four planes/chip, 16 KiB logical page, 8 channels, 2.0 GB/s channel and 8.0 GB/s PCIe are modeled geometry/bandwidth; ordinary be-enc LSB tR is 28 µs. CR 9.7 µs is outside this task. The paper discusses 45 nm synthesized logic and measured read behavior; it does not claim a fabricated full AiFChip prototype.

3. [SNU Department announcement, 2026-09-08](https://cse.snu.ac.kr/ko/community/notice/25557?pageNum=5) from the same principal investigator's lab describes a project to develop an AiF virtual ISA/command interface, functional GEMV simulator, NVMeVirt integration, host runtime, async commands and correctness/performance environment; it explicitly says that project is not fabricating a physical chip. This documents a development objective at that date, not a claim the 2025 timing simulator did not exist, not evidence that no private simulator or later release exists, and not a disclosure of hardware field widths or PE count. The announcement links no implementation.

4. [Upstream NVMeVirt repository](https://github.com/snu-csl/nvmevirt) supplies the generic emulator that the AiF authors extended. Its generic source/README cannot establish AiF-specific implementation or proprietary NAND datapath. Public repository search on 2026-11-03 found the following **AiF-like reproduction** repositories with a default branch named `research/aif-reproduction-v1`; affiliation with the AiF authors or use of their original extension has not been established:
   - [NVMeVirt reproduction at c01dbef3893eefcbace4dbad03ceee32a37b6048, AIF.md](https://github.com/Chanyeong-Yoon/nvmevirt-aif/blob/c01dbef3893eefcbace4dbad03ceee32a37b6048/AIF.md), [protocol header](https://github.com/Chanyeong-Yoon/nvmevirt-aif/blob/c01dbef3893eefcbace4dbad03ceee32a37b6048/aif.h) and [model/command handler](https://github.com/Chanyeong-Yoon/nvmevirt-aif/blob/c01dbef3893eefcbace4dbad03ceee32a37b6048/conv_ftl.c#L1119). Its reproduction ABI uses 32-bit `input_dim`, `input_nbytes` and `output_nbytes` fields, with a 64-byte packed GEMV request. The handler checks nonzero byte lengths, a dummy-output flag and a matching posted layout; it performs PRP copy/checksum and returns dummy output, not weight-backed GEMV. This is a software implementation example, **not the AiF paper's disclosed native command encoding or a hardware capability test**. A 128-byte nonzero length passing one software check does not establish that the request is valid end-to-end or that a physical PE supports it.
   - Its timing code uses `max_plane_pages * 9.7 µs` and a 6.4 GB/s modeled chip byte rate, taking the maximum, then modeled output gather. This folds the same CR latency into every page and has no explicit 28-µs ordinary first read; it is outside the no-CR contract. It has no MAC lane parameter, row-completion delay, ECC datapath simulation, page-register contention or FIFO-depth/backpressure simulation from which r128 execution could be measured. Its README explicitly disclaims numerically correct GEMV or a cycle-accurate flash implementation.
   - [Matching llama.cpp reproduction at 4da1ec75d6a2071ad242a4b362d620fccd6271c7](https://github.com/Chanyeong-Yoon/llama.cpp-aif/blob/4da1ec75d6a2071ad242a4b362d620fccd6271c7/AIF.md) describes shadow/replace/parallel modes; replacement outputs are dummy. Its [host code](https://github.com/Chanyeong-Yoon/llama.cpp-aif/blob/4da1ec75d6a2071ad242a4b362d620fccd6271c7/common/common.cpp#L1803) explicitly defines `activation_elem_size = sizeof(float)` and sizes output similarly, and claims a particular host's 512 KiB passthrough mapping limit. Those are **that reproduction's** software choices, not AiF paper claims about native input representation, INT8 multiplier inputs, output encoding, or a universal NVMe hardware limit. No reproduction binaries were built or executed here.

## A conditional r128 contract and bookkeeping

The following is a proposed, reviewable hardware/software contract, not a claim about stock AiF and not a new method or measured performance:

- A row-major logical `H × 128` signed W8 matrix has 128 complete rows in each 16 KiB page, assuming no row padding, no scale/bias interleaving and the paper's page size means 16,384 weight bytes before any implementation-specific ECC/spare bytes. ECC correction precedes arithmetic. The input has 128 A8 elements, staged in the relevant input latches, in an explicitly declared signed representation; page-register addressing supplies the matching activation index repeatedly as consecutive rows are processed. Host/controller performs placement, submits correct dimension and length, and provides input; whether existing AiF already supports this exact layout is unknown.
- A PE design with a programmable row-length counter, correct lane-to-input indexing and reset/emit at every 128 weights can implement it without adding arithmetic lanes **only if** existing datapaths can address/broadcast these operands, accept 128 as a dimension, carry enough accumulator precision, separate plane streams, and drain row outputs at the required speed. Any missing ability needs its own circuitry, control, interface or storage. The counter may already exist; neither its presence nor its absence is disclosed. Muxing/latching, four-plane arbitration, ECC alignment, supported `aif_post` packing and input lifetime after a command must not be assumed free. Account per-command setup and input fanout, even for small operands. Padding 128 to a larger physical extent is an alternative only if those padded weight bytes and their sensing/compute costs are charged.
- With signed two's-complement full-range A8/W8 values `[-128,127]`, 128 products can sum to +2²¹; a signed exact accumulator needs **23 bits** including sign. If both operands are guaranteed `[-127,127]`, maximum is 128×127²=2,064,512 and 22 signed bits suffice. In either case I32 has sufficient numerical range. This is arithmetic analysis, not disclosure that AiF outputs I32. Native output width, saturation/rounding and reduction ordering are unspecified. A proposed raw-I32 output plus host `s_x*s_w` scaling must pay scale/bias transfer and host arithmetic, and satisfy the chosen reference's rounding; it does not automatically match an F32 or W8A8 implementation bitwise.
- Illustrative aligned shape `H=2048, r=128`: matrix is 262,144 bytes or 16 full pages. If four chips each access four planes and each gets 512 output rows, every plane receives one 16 KiB page. Each chip supplies 65,536 weight bytes and 512 output values. This assumes complete rows per page, the desired four-chip/four-plane mapping, accessible ECC bytes and concurrent plane operation, none newly verified in AiF. A zero-fill remaining physical row width `H=2048` would change read/compute cost and cannot be equated to the 256 KiB layout.
- If the output protocol uses four bytes per result, this example produces 8192 bytes total, 2048 bytes/chip, irrespective of whether streamed. At 2 GB/s per modeled channel, ideal ONFI payload time is at least 1.024 µs with four distinct channels or 2.048 µs if the four chips share only two channels; 8 GB/s PCIe needs another aggregate 1.024 µs of payload service. These are per-resource lower bounds, not automatically additive elapsed times. FIFO depth, packet framing, polling, arbitration, backpressure, pipeline overlap and scale/bias traffic remain unknown. More narrow-chip sharding increases outputs per chip; SREG status is not an output storage capacity.
- Each chip processes 65,536 signed 8-bit products. Under the **hypothetical** design that has `L` lanes at 200 MHz and sustains one product per lane per cycle, the arithmetic service is at least `65536/(200e6 L)` seconds; reaching 28 µs *steady-state processing per 64 KiB* requires `L ≥ 12`, with perfect utilization. AiF does not reveal `L`, so this is a conditional requirement, not a claim its chip has 12 lanes or can do one wave in 28 µs. The ECC decoder's published 6.4 GB/s gives 10.24 µs per 64 KiB of decoding service, not a MAC throughput. Whether single-wave ECC and GEMV can start during sensing or must follow completion is not disclosed: `max(28 µs, ECC service, MAC service, ONFI/PCIe service)` is only a resource lower bound, not an established pipeline schedule, and real command-to-output latency may be longer.

## Cost triangulation and missing evidence

[SLIM Table 2 and §7.1](https://arxiv.org/html/2507.09201v1) reports a **different** die-level PE point: 16 MACs plus 64 KiB SRAM, 0.07 mm² and 27.0 mW at 1 GHz, with its own modeled/synthesized node and SSD system. It is evidence that authors have modeled finite MAC/SRAM datapaths, not an AiF lane count or directly transferable incremental area. [NITRO §III-D/IV-A](https://arxiv.org/html/2608.11920) describes 128×128 tiling in an analog NAND-PIM baseline and separate digital accumulators/ADC/DRAM buffering; its analog representation and bit-serial dataflow are different from AiF's corrected ordinary-read digital multiplier, so it cannot verify AiF row packing or throughput.

Still required for a quantitative claim: original author RTL or an authoritative command/driver specification; supported vector lengths and wire numeric widths; input-latch replication, alignment and per-plane read bandwidth; page-row reset/indexing and ordering; integer accumulation width and scale semantics; MAC lane count and cycle rate/utilization; ECC–PE–sensing overlap; FIFO depth, service and backpressure; measured or cycle-accurate small-command latency; and controller LBA/IFP-block fragmentation/dispatch behavior. Until sourced, sweep these assumptions and share identical compatible extensions and overhead models with all baselines. No author-published public AiF RTL or original modified NVMeVirt source was identified in this bounded search; that is not proof of absence.
