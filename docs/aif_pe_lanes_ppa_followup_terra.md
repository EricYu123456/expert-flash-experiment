# AiF short-rank PE lane/area source audit

2026-11-03 UTC. Source-only, bounded search; no candidate data/code, model, synthesis, RTL execution, installation, or author contact. This note addresses an explicitly **hypothetical** 16 INT8 products/cycle/chip design at 200 MHz, not a newly established AiF native configuration.

## What the AiF artifact evidence establishes

[AiF, ISCA 2025, §§4.4 and 6.1](https://doi.org/10.1145/3695053.3731073), checked against local `paper/aif.txt:724–782, 816–827, 870–877, 919–924`: 200 MHz and 45 nm are synthesis conditions; PEs use INT8 multipliers and an adder tree; reported PE block is 0.026 mm² and 3.98 mW. The paper describes four 16-KiB planes/chip, 28 µs ordinary LSB tR under be-enc, and a 6.4 GB/s **ECC** decoder throughput. It does not quantify product lanes, initiation interval, operand delivery bandwidth, row-boundary behavior or short-rank utilization. Per parent’s visual inspection of the original PDF, Fig. 14 has PE box and four-plane arrows, not a labeled multiplier count. Those figures and the area total alone do not determine 16 or 32 lanes.

Fresh source avenues checked: [ISCA 2025 official artifact-evaluation rules](https://www.iscaconf.org/isca2025/submit/ArtifactEvaluation.php) say participation and an appendix are voluntary; the [AE submission portal](https://isca2025ae.hotcrp.com/) gives only aggregate submission counts in the accessible public view, not an identified AiF PE artifact. Title/author searches over public GitHub and web and the paper text did not locate an AiF-author PE RTL, signed short-vector microarchitecture, standalone synthesis report, or lane-count appendix. This is a bounded search result, **not proof that no artifact exists**; publisher direct fetch was blocked, and no authors were contacted. The generic upstream [NVMeVirt](https://github.com/snu-csl/nvmevirt) is an emulator, not evidence of the AiF-specific PE. §6.1 describes the authors' virtual device as producing dummy output based on a timing model; this does not supply an independently validated MAC rate.

## New primary-source implementation comparisons — not AiF

1. [Jang & Tambe, BlockDialect, ICML 2025, §4 and Table 5](https://proceedings.mlr.press/v267/jang25c.html), [author paper PDF](https://raw.githubusercontent.com/mlresearch/v267/main/assets/jang25c/jang25c.pdf): the authors model individual MAC units in SystemVerilog and synthesize with Synopsys Design Compiler at 0.5 GHz, Nangate 45 nm OpenCell; Table 5 reports **one INT8 MAC** total 554.34 µm² and 331.17 µW, with separately listed multiplier and accumulator fields. It is an author's technology-mapped comparison point at its own 500 MHz, workload/activity and implementation assumptions, not a 16-product reduction tree, AiF PE estimate, measured silicon, or evidence that AiF can fit any particular number of lanes. An array's shared reduction, extra registers, control, PB interfaces, clock, physical timing, voltage, switching activity and routing all change its result; 16 × the table number is not a defensible area or power estimate for the proposed complete chip.

2. [NVIDIA NVDLA official architecture specification](https://nvdla.org/hwarch.html) discusses parallel input and output dimensions, associated buffer bandwidth and partial-utilization losses; [the official NVDLA RTL repository](https://github.com/NVDLA/hw/tree/nvdlav1) provides Verilog, synthesis examples and testbench, and describes a much larger 2048 INT8-MAC fixed release. It is a **different CNN accelerator**, neither AiF nor a published 16-lane 45-nm NAND-chip PPA result. Its usefulness here is to define comparable constraints: multiplier instance count by itself does not prove every lane is fed or useful on a row-packed workload. No RTL was executed or synthesized.

3. [junyoung-sim signed INT8 multiplier design](https://github.com/junyoung-sim/multiplier) independently reports a five-stage pipelined signed multiplier and physical-design comparisons at **180 nm**. It does not include the target AiF dot/accumulator architecture and its area/power cannot be substituted into a 45-nm AiF budget. It is a concrete source example of pipeline latency, enables, and area/performance dependence, not proof of numerical AiF hardware cost. The authors' own reported results were not reproduced here.

These comparisons supply useful implementation references, but none resolves native AiF 16-lane feasibility or PPA. The appropriate next evidence, if sought later, is an AiF-authored PE RTL or gate-level netlist and synthesis/STA/power reports specifying exact libraries/corner, clock, operand widths, lane/adder topology, data mapping, ECC/PB interface and activity; or an independently synthesized integrated 16-lane r128 prototype with the same information. A single scalar multiplier PPA figure is insufficient.

## Arithmetic and time-model bounds

Let **explicit model assumptions** be four concurrently sensed 16-KiB LSB data pages/chip, one useful INT8 multiply per sensed weight byte, every byte used, row packing supported, and one 200-MHz chip-wide PE capable of accepting 16 products each cycle at 100% utilization. These are not native-AiF measurements. Payload per hypothetical wave = `4×16×1024=65,536 B`; its implied ordinary array payload average is `65,536/(28 µs) = 2.3406 GB/s` (decimal GB). This is an average over the assumed wave, not an instantaneously available PB/ECC output rate. Four simultaneous planes, command overhead, page transfer, ECC, and all-lane data supply must be checked separately.

- 16 × 200 MHz = **3.2 Gproducts/s peak**. Ideal PE service demand = `65,536/(3.2×10^9) = 20.48 µs`; assuming 128 weights/row, it is 512 complete rows per chip and 8 issue cycles/row, without pipeline fill/drain, stalls, partial rows, bookkeeping or output throttling. Arithmetic compares 2.3406 Gproducts/s offered average with 3.2 Gproducts/s peak, i.e. 73.14% average lane utilization if the assumed source is fully smoothed and no overhead exists. Nominally `ceil(65,536/(200e6×28e−6))=12` perfect lanes meet that average, but this is a mathematical rate comparison—not a practical sufficient lane count or an AiF measurement.
- If the paper's 6.4 GB/s ECC number can be used as a sustained **aggregate per-chip effective corrected-data rate** for these pages, ideal ECC service demand for 65,536 payload bytes is 10.24 µs. This is an additional explicit assumption: actual codeword/parity delivery, multiple-plane decoder ownership, release timing and stalls are not characterized by the number alone. ECC 6.4 GB/s is not a PE throughput and does not establish PE/ECC/sensing overlap.
- For a completion metric that includes completing the ordinary sensing/discharge **and** completing the wave’s corrected products, independent peak resource work yields an optimistic lower bound `T ≥ max(28, 10.24, 20.48) µs = 28 µs` under all assumptions above. The max is a **lower bound only**, not proof a 28-µs schedule exists. Dependency, input staging, latch availability, output FIFO drain and burstiness can make it longer. Some processing during discharge is not excluded by the text, but no release timing proves it.
- A hypothetical fully serialized model that waits for the full 28 µs and then completes all ECC before all PE has ideal `28+10.24+20.48 = 58.72 µs` before input, command, output and other overhead. This is one conservative **modeled schedule**, not an upper bound on actual hardware, nor proof the native design is serial. With stalls, retries, shared-channel contention, additional data, or other costs there is no demonstrated finite upper bound from these three service times alone. Partial overlap falls between such simple ideals only when the modeled stages and per-stage demands are held fixed and no extra overhead is introduced.

For short r128, report parameter sweeps of effective aggregate product issue rate/utilization, plane concurrency, ECC effective rate, latch/port sharing and release time, FIFO/out drain, command/input overhead, row-reset and pipeline latency. Distinguish first-wave completion latency from long-run initiation interval and finite two-cohort makespan. A continuous stream can have an initiation interval near its bottleneck while a finite two-wave schedule still pays fill/drain; none of these values follows from the ECC number alone.
