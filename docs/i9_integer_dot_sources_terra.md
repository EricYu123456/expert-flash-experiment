# Intel i9-14900KS integer-dot ISA: primary-source review

2026-11-03 UTC. Scope: source/documentation and arithmetic only. No candidate code, weights, book/question/target payload, execution or benchmark was accessed. All performance and target-host feature availability remains to be established on the actual target system.

## Target SKU, hybrid cores, and the feature evidence boundary

- [Intel's i9-14900KS product page](https://www.intel.com/content/www/us/en/products/sku/237504/intel-core-i9-processor-14900ks-36m-cache-up-to-6-20-ghz/specifications.html) specifies 8 P-cores, 16 E-cores and 32 threads, lists AVX2 and Intel Deep Learning Boost, and lists a maximum advertised memory bandwidth of 89.6 GB/s. It does **not separately enumerate AVX-VNNI** in its abbreviated extension list. It does not establish any particular P/E-core throughput or sustained memory bandwidth in our configuration.
- Intel's [13th/14th-generation Raptor Lake datasheet § AVX2 VNNI](https://edc.intel.com/content/www/us/en/design/products/platforms/details/raptor-lake-s/13th-generation-core-processors-datasheet-volume-1-of-2/009/intel-avx2-vector-neural-network-instructions-avx2-vnni/?language=en) lists AVX2 VNNI for its covered Raptor Lake/Refresh processor families while cautioning that availability can vary by SKU. The [14th-generation desktop product brief](https://www.intel.com/content/www/us/en/products/docs/processors/core/core-14th-gen-desktop-brief.html) lists AVX2 and Deep Learning Boost. These sources make VEX AVX-VNNI a serious target implementation to check, but do not themselves provide a 14900KS per-core CPUID capture.
- Intel's [12th-gen hybrid guide](https://www.intel.com/content/www/us/en/developer/articles/guide/12th-gen-intel-core-processor-gamedev-guide.html) and [hybrid whitepaper](https://cdrdv2-public.intel.com/685861/211115_Hybrid_WP_1_Introduction_v1.2.pdf) specifically state AVX-VNNI was provided across both P/E cores and AVX-512 disabled for that **12th-generation** hybrid design. This is architecture-family context, not direct per-core verification of this 14th-gen SKU or evidence that performance per core is the same. Pinning/detecting each target core, recording actual hardware/OS CPUID and vector-state support, and using appropriate thread placement remain necessary. Eight physical P-core workers differ materially from 8 arbitrary logical processors or 8 cores on EPYC 9354; no numerical scaling is claimed.
- [Intel SDM CPUID and instruction reference](https://cdrdv2-public.intel.com/835781/325462-sdm-vol-1-2abcd-3abcd-4.pdf) describes `CPUID.(EAX=7,ECX=1):EAX[4]` for AVX-VNNI; separately `EDX[4]` at that subleaf is AVX-VNNI-INT8. Verify leaf/subleaf availability and AVX/OSXSAVE plus XCR0 support for XMM/YMM state before dispatch. Virtualization, OS configuration, microcode and permitted affinity can affect what the application sees. Do not infer an actual CPUID result from the docs or silently execute an unsupported ISA.

## Correct byte dot products

- The [Intel SDM VPDPBUSD instruction entry](https://cdrdv2-public.intel.com/789581/325383-sdm-vol-2abcd.pdf) defines VEX.128 and VEX.256 **AVX-VNNI** forms: unsigned byte × signed byte, groups of four products accumulated into signed I32 elements **without saturation**. The saturating form is `VPDPBUSDS`, with an additional `S`. In a 256-bit register each instruction consumes 32 unsigned/signed byte pairs across eight I32 partial lanes; a horizontal reduction is still needed. Non-saturation is not infinite precision: I32 destination addition has finite width, and all intermediate lane and final reduction bounds must be safe.
- Intrinsics in the Intel SDM and [LLVM's original `avxvnniintrin.h` documentation](https://clang.llvm.org/doxygen/avxvnniintrin_8h.html) name the 256-bit VEX form `_mm256_dpbusd_avx_epi32(acc, unsigned_bytes, signed_bytes)` and the 128-bit form `_mm_dpbusd_avx_epi32`. They differ from the Intel/LLVM `_mm256_dpbusd_epi32` EVEX AVX512-VNNI+VL intrinsic; do not accidentally require AVX-512 because the name lacks `_avx_`. The 512-bit form requires a separately reported AVX-512 capability and cannot be assumed on this target. GCC documents separate [`-mavxvnni`, `-mavx512vnni`, `-mavxvnniint8`](https://gcc.gnu.org/onlinedocs/gcc/x86-Options.html) switches. Compiler version, generated disassembly, runtime dispatch and fallbacks must be verified when actually implementing, not assumed from the switch alone.
- [Intel's instruction extension reference](https://cdrdv2-public.intel.com/671368/architecture-instruction-set-extensions-programming-reference.pdf) defines direct signed×signed byte `VPDPBSSD` under the separate **AVX-VNNI-INT8** feature. The basic AVX-VNNI bit does not imply that extension. The target SKU's AVX-VNNI-INT8 status is not established here; do not select its instruction without independent CPUID/OS support.
- For signed int8 activation `q_i` and signed int8 weight `w_i`, define `u_i=q_i+128` in 0…255. The byte-level mapping is XOR the original two's-complement bit pattern with `0x80`, reinterpreted as unsigned. Exact integer algebra gives `Σ q_i w_i = Σ u_i w_i − 128 Σ w_i`. A per-row signed `Σw_i` can be computed offline once and stored with the weights, provided it reflects the exact stored quantization, dimensions, padding and reorder. Add a first-step correction or subtract after horizontal reduction only with safe accumulator widths; if there are per-block scales, split the sum and correction at the same scale boundaries and perform each required rescale. Tail masking/zero-padding must preserve the identity: padded signed `q=0` maps to **u=128**, unless the corresponding weight is zero or the precomputed correction excludes that entry consistently.
- Worst-case bounds for q,w∈[-128,127]: `|Σu_i w_i| ≤ 32640D`, `|128Σw_i| ≤ 16384D`, `|Σq_i w_i| ≤ 16384D`. Thus for D=2048 the first quantity is ≤66,846,720 and the correction magnitude ≤33,554,432; for D=14336 the first is ≤467,927,040, each representable in signed I32, including per-lane accumulation under these dimensions. These loose bounds establish no overflow for those lengths if the implementation also handles reduction/correction without C/C++ signed-overflow UB. They are theoretical worst-case bounds, not tests or measurements.
- One precomputed I32 row sum is 4 bytes/row: additional raw metadata is 3.125% of a 128-byte W8 row or 0.1953125% of a 2048-byte W8 row, before alignment, paging/cache-line amplification, quantization scales, bias, indices and transfer. Charge once per stored row (or per scaled block) and for actual access/cache placement. Computing the sum online is a separate measured-cost option. Output integer exactness does not by itself imply bitwise equivalence to the reference's FP32 reduction or quantization: I32 results can exceed 2²⁴ and floating-point rescaling/order may change rounding. The reference, activation A8 quantizer, per-block metadata, conversion, horizontal reduction and any post-scale/bias/combine must be identical or separately quality-evaluated.

## AVX2-only fallback and saturation trap

- AVX2 can sign-extend int8 elements to int16 and use `_mm256_madd_epi16` (`VPMADDWD`) for pair products/sums to I32, then accumulate and reduce. For source values originally in int8 range the special signed-I16 extreme overflow case is impossible in each pair; accumulated sums still need the same I32 overflow analysis. [Intel instruction reference](https://cdrdv2-public.intel.com/774492/325383-sdm-vol-2abcd.pdf) specifies the operations. This is a possible correct fallback, not evidence it is the fastest.
- AVX2 `_mm256_maddubs_epi16` / `VPMADDUBSW` multiplies unsigned bytes by signed bytes but **saturates each adjacent pair to signed I16** ([Intel reference](https://www.intel.com/content/dam/www/public/us/en/documents/manuals/64-ia-32-architectures-software-developer-vol-2b-manual.pdf)). For example 255×127 + 255×127 = 64,770 exceeds 32,767 and saturates before later I32 addition. An unchecked `maddubs` shortcut is therefore not equivalent to the exact full-range identity. Input restriction or decomposition may avoid saturation only with a demonstrated bound and properly charged extra operations.
- Runtime on real EPYC 9354 with eight physical cores is a useful proxy for a specific tested implementation, not the i9-14900KS ISA/throughput. An optimized target-legal VEX AVX-VNNI implementation, AVX2 fallback, CPU affinity, thread counts, cache footprint and actual source/activation precision must be measured under the same workload and quality contract before making a target speed claim. No claim is made that VNNI necessarily wins in an entire memory-bound application: packing, activation conversion, row sums, scaling, cache traffic and dependencies can dominate.
